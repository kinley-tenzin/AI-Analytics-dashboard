# Embedded Superset dashboards in the DrukSmart website (Task 10.5)

**Status: working and tested.** The HR and Accounts pages of the website show the governed Superset
dashboards with Superset's official **Embedded SDK** (`@superset-ui/embedded-sdk` 0.4.0) and
**guest tokens**. Viewers never sign in to Superset.

## 1. Flow and trust boundaries

```
Browser (127.0.0.1:8000, Django session)                 Superset (127.0.0.1:8088, separate origin)
 1. POST /api/v1/portal/dashboards/hr/guest-token/  ─┐
    (session cookie + CSRF)                          │ Django: user signed in? dashboard visible?
                                                     │ module in the user's scope? dashboard uses
                                                     │ only that module's datasets? branch rules?
                                                     ├─ 2. as the PORTAL SERVICE ACCOUNT:
                                                     │    POST /api/v1/security/guest_token/
                                                     │    {resources:[this dashboard], rls:[...]}
 3. {token, embedded_id} ◄────────────────────────────┘
 4. SDK creates <iframe src=".../embedded/<uuid>">  ──► Superset checks Referer = allowed website origin
 5. charts query /api/v1/chart/data with X-GuestToken ─► Superset: signature + expiry; only charts of
                                                         that dashboard; payload not modified;
                                                         RLS rules ANDed into every query
 6. before expiry (5 min) the SDK calls step 1 again ──► a signed-out / downgraded user gets no new token
```

**What each system enforces**
- **Django** (`backend/portal/dashboards.py`) decides access from the user's Django scope, never from browser input:
  - only visible dashboards of the user's own modules;
  - the dashboard must use only datasets of its module (from `superset/definitions/access.yml`; checked on every token, so a creator adding an Accounts chart to an HR dashboard makes it unavailable instead of leaking);
  - branch managers get `branch_key IN (...)` RLS rules for every branch-filtered dataset;
  - a branch manager is refused if the dashboard contains a dataset that can be neither branch-filtered nor is branch-neutral, or if they have no branch;
  - malformed branch keys are refused.
- **Superset** enforces the signed token:
  - one dashboard;
  - only that dashboard's charts and native filters;
  - no modified chart payloads;
  - the RLS rules applied to every query, including aggregates, CSV export and Drill by.
- **Important:** Superset's role-based RLS does **not** apply to guest users, so the branch rules must come from Django. They do; this is tested.

## 2. Configuration

| Where | Setting | Why |
|---|---|---|
| `superset/docker/superset_config.py` | `EMBEDDED_SUPERSET: True` | Enables the embedded view and guest tokens |
| | `GUEST_TOKEN_JWT_SECRET = _required("SUPERSET_GUEST_TOKEN_SECRET")` | Superset's default secret (`test-guest-secret-change-me`) is public; anyone knowing it could forge tokens without RLS. The container refuses to start without our secret |
| | `GUEST_TOKEN_JWT_EXP_SECONDS = 300` | Tokens live 5 minutes; the SDK renews them through Django |
| | `GUEST_ROLE_NAME = "DrukSmart Embedded Guest"` | The guest's permissions (below) |
| | `TALISMAN_CONFIG`: `frame-ancestors 'self' http://127.0.0.1:8000`, `frame_options = None` | Only the website may frame Superset (X-Frame-Options cannot name another origin) |
| `superset/definitions/access.yml` | role **DrukSmart Embedded Guest** (base `guest`) | Viewer permissions with **no dataset access of its own**, minus everything that leads out of the website into Superset (Explore / "Edit chart", "View query", share links) |
| | role **DrukSmart Portal Service** (base `service`) | Viewer access to the approved datasets, plus `can_grant_guest_token` and `can_set_embedded`. Cannot edit charts or dashboards, and has no SQL Lab (tested) |
| | `embedding.branch_neutral_tables: [data_freshness]` | Datasets without branch data |
| `superset/scripts/bootstrap.py` step 6 | Embedded configuration of the default dashboards (allowed domain = `DRUKSMART_WEB_ORIGIN`); service account | Idempotent, like steps 1–5 |
| `.env` (generated by `create_local_env.py --add-missing`) | `SUPERSET_GUEST_TOKEN_SECRET` (64 characters), `SUPERSET_PORTAL_SERVICE_USER/_PASSWORD`, `DRUKSMART_WEB_ORIGIN` | Secrets are local and never committed |
| `compose.yaml` | Superset containers get the guest secret and web origin. The backend gets the service account and the Superset internal/public URLs, but **never** the admin password or the signing secret | Least privilege (unit-tested) |
| Website | `frame-src http://127.0.0.1:8088` in the app's CSP; the iframe sends `Referer` with `strict-origin-when-cross-origin` (origin only), because Superset checks it against the allowed domains | Django's own policy stays `same-origin` |

**Cookies and origins.**
- The website (8000) and Superset (8088) are different origins. Serving the website from Django does **not** give the iframe the Django session, and does not make Superset same-origin.
- Guest tokens travel in the `X-GuestToken` header, not in cookies. The parent page never calls Superset's API (no CORS needed); the SDK talks to the iframe with `postMessage`.

## 3. Features inside the embedded dashboards (tested in Edge)

| Feature | Guest (website viewer) |
|---|---|
| Native filters (snapshot date, period, organisation, branch, department, …) | Yes, limited to the user's rows |
| Cross-filtering (click a bar or slice) | Yes |
| **Drill by** (right-click a value, choose a dimension) | Yes, RLS applied (branch manager: departments sum to the branch total) |
| Drill to detail (raw rows) | **No.** No DrukSmart role has `can_samples`; raw employee-level rows are not exposed |
| Chart menu: View as table, full screen, description | Yes |
| **Download → Export to .CSV / Excel / image** | Yes. The branch manager's CSV contains only their branch (tested) |
| Edit chart / Explore / View query / Share | No (removed from the guest role) |
| Dashboard editing | No. The HR / Accounts Managers use the "Edit in Superset (separate sign-in)" link (§4) |

## 4. Dashboard authoring (approved prototype limitation)

- **Who sees the link (ADR-044):** the **HR Manager** (HR page) and the **Accounts Manager** (Accounts page), and the administrator, see **"Edit in Superset (separate sign-in)"** on the HR and Accounts pages.
- **Where it goes:** it opens the dashboard in Superset's native editor in a new tab. Superset asks for the manager's **Superset** account (demo: `demo_hr` or `demo_accounts` with `SUPERSET_DEMO_USER_PASSWORD`).
- **Why no editing inside the website:** the Embedded SDK only supports viewing, and CLAUDE.md §2 forbids a custom dashboard designer.
- **Creating a dashboard:** a manager builds a **new** dashboard (Superset → Dashboards → + Dashboard) with their own charts on the approved datasets.
  - **Limitation (Superset, tested):** with `DASHBOARD_RBAC` on, Superset allows *Save as* (copy) only for a dashboard's **owners**. The official templates are owned by the administrator, so creators cannot copy them.
  - Making managers co-owners would let them change the governed templates, so it is not done. The administrator can copy a template once and make the manager the owner of the copy.
- **Publishing a manager's dashboard** (website → **Manage dashboards**; the manager for their own module, the administrator for both):
  1. The manager enters the dashboard's id or slug; the module is their own.
  2. The backend enables embedding for the website only, and refuses the dashboard if it uses data of another module.
  3. It starts **hidden**; the manager makes it visible.
  4. It then appears as a tab on that module's page for every viewer of the module.
- **Tested end to end** against the running Superset (`tests/superset/test_authoring_live.py`):
  - the HR Manager builds a dashboard with their own Superset account;
  - the HR Manager publishes it through the website;
  - it is hidden until made visible;
  - an HR viewer then gets a guest token that opens it, and an Accounts viewer is refused;
  - a dashboard mixing HR and Accounts data cannot be published;
  - the HR Manager cannot change or copy the official templates, and gets no data from Accounts datasets.

## 6. Known limitations
- **Token lifetime:** a guest token stays valid for up to 5 minutes after sign-out or a role change. That is the renewal interval; it is not revoked instantly.
- **Separate Superset sign-in** for authoring (approved; SSO is possible future work).
- **Templates:** managers cannot *Save as* the official templates (Superset `DASHBOARD_RBAC` owner rule); they build new dashboards (§4).
- **Superset browser warning:** Superset 6.1's image has no `service-worker.js`, so the browser console shows a harmless 404 from the iframe.
- **Dataset-domain caching:** dashboard metadata is cached for 5 minutes in each backend worker, so a manager's change to a dashboard's datasets is re-checked within 5 minutes.
